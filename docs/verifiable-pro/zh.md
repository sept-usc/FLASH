FLASH 是面向机密大语言模型（LLM）推理的检查点与恢复系统。它保存恢复服务所需的数据状态，同时限制推理必须暂停的时间。该设计结合加密检查点存储与 NVIDIA 驱动中的内存跟踪机制，论文在单张 NVIDIA H100 GPU 与 Intel Trust Domain Extensions（TDX）上进行了评测。它解决的是一个具体的运维问题：如何让受保护的推理状态能够恢复，同时避免服务反复停下来导出整张 GPU 的内存。[^1]

论文题为《FLASH: Fault-Led, Attested, Secure Hybrid-Key Checkpoint for Confidential Inference》，作者为 Jonghyun Lee、Taewoon Kang、Yongqin Wang、Rachit Rajat、Mengyuan Li、Gunjae Koo、Daniel Wong 和 Murali Annavaram，会议为 ACM SIGOPS ATC 2026。[^1]

## 为什么机密推理更难建立检查点

推理过程中，模型会积累键值缓存（KV cache），保存已处理 token 的注意力状态。丢失缓存意味着活动请求已经完成的部分计算也随之丢失。检查点保存这些状态，使恢复能够从已保存的位置继续。在机密部署中，CPU 与 GPU 的可信执行环境（TEE）设计用于在各自硬件威胁模型内，保护模型和请求数据不被恶意云主机读取。[^1]

这种保护改变了检查点的数据路径。GPU 数据在被保存之前，必须经过不可信的 PCIe 连接。H100 的复制引擎会加密离开 GPU 受保护内存的数据。常规安全检查点随后在 CPU TEE 内解密收到的数据，再用检查点密钥重新加密。原本带宽已经受限的传输，因此又增加了 CPU 密码运算。[^1]

在论文的实验环境中，机密模式使传输带宽从约 40 GB/s 降至 7.3 GB/s。仅按这一速率搬运 80 GB，就需要约 11 秒，尚未计入额外的检查点加密。如果整个过程都暂停推理，建立检查点就会成为用户能够感受到的服务中断。[^1]

## 复用 GPU 已经生成的密文

FLASH 保留复制引擎已经生成的密文。定制的驱动接口获取加密内存页，以及对应的初始化向量（IV）和认证标签。检查点直接保存这些数据，从频繁执行的检查点路径中移除 CPU 先解密再加密的环节。[^1]

生成的镜像包含两个密钥域。GPU 页继续使用源会话的设备到主机密钥保护；CPU 状态和源 GPU 密钥则由检查点密钥保护。保存的元数据使恢复程序能够重建认证和解密原始 GPU 页所需的上下文。数据进入目标 GPU 时，再经过目标端的受保护传输路径。[^1]

这改变了密码运算发生的时机。FLASH 在每次建立检查点时省去重复的 CPU 加密工作，恢复时仍然需要重建并解密保存的状态。因此，检查点停顿缩短与恢复延迟应当分别理解。[^1]

## 后台复制，再补拷被修改的内存页

保留密文降低了每字节的处理成本。FLASH 还减少了暂停服务期间必须搬运的数据量。它先在推理继续运行时复制 GPU 内存。后台复制期间的写入可能让已保存的页过时，因此系统必须识别哪些页需要再次复制。[^1]

FLASH 拦截内存分配调用，使相关分配纳入 NVIDIA 统一虚拟内存（UVM）的管理。它将被跟踪的页设为只读，后续写入就会触发缺页异常。驱动在允许写入继续之前，将对应区域记入脏页位图。跟踪粒度为 2 MB；与逐个跟踪 4 KB 页相比，这种选择接受一定程度的多记，以减少缺页异常处理的次数。[^1]

后台复制结束后，FLASH 暂停执行，补拷脏页增量，再恢复推理。这就是 stop-and-copy 阶段。其耗时取决于跟踪窗口内被修改的数据，而不是 GPU 的全部内存占用。该机制位于 LLM kernel 之下，不需要离线分析 kernel 的 PTX 代码。[^1]

## 恢复镜像仍然包含静态数据

模型权重在初始化后通常保持不变。按照论文中的静态分配设计，FLASH 首次捕获静态状态后，会在后续检查点镜像中复用这份数据。相关页仍受写保护；后续写入会将受影响区域提升为动态状态。恢复时，静态和动态数据都需要恢复。[^1]

公开评测程序通过 `v3-static` 提供静态分类。其默认路径依据主机到设备传输的分配标记进行识别，学习路径则需要单独启用 `--learn`。在将一次运行与论文设计对照时，需要区分这些实现选择。[^2]

## 将保存的状态绑定到密钥、页位置与新鲜性

当保存镜像的主机不可信时，仅有机密性还不够。主机可能修改内存页，将真实页面放到错误位置，或者提供旧检查点。FLASH 的安全协议分别处理这些问题。[^1]

认证标签保护加密页的内容。经过认证的清单记录页位置与密码元数据，其哈希绑定到由 TDX 签名的新鲜性报告。一个可信的远程证明服务保存检查点密钥和最新的新鲜性记录。恢复时，协议先核对记录，再向通过检查的机密虚拟机释放密钥。[^1]

远程证明提供该环境加载了哪些软件的证据；设计仍然信任这些软件正确执行检查。它也信任 CPU 与 GPU 的安全机制、客户机内核和驱动，以及远程服务保存的状态。论文分析不涵盖针对恶意主机的可用性保障，也不隐藏检查点大小、访问模式或时间信息。[^1]

## H100 评测测量了什么

评测使用单张处于机密计算模式的 80 GB H100、Intel TDX 和 vLLM 0.8.5。工作负载包括 Llama-3.2-1B、Qwen-2.5-7B 和 Llama-2-13B，分别运行短上下文 Chatbot 与长上下文 Reasoning 场景。检查点镜像暂存于由 DRAM 支撑的 tmpfs。[^1]

论文对 FLASH 及其去掉静态分类的消融版本 FLASH-SC 汇总后，报告平均 stop-and-copy 延迟为 1.2 秒。相对于基于 PhoenixOS 的对照实现 PhOS，论文报告延迟降低 9.4 倍；相对于检查点间隔为一分钟的 GCR，降低 7.8 倍。对照系统是在相同机密计算栈上重新实现的数据路径，原始公开 artifact 无法在这一平台上原样运行。[^1]

这些测量给出的是该实验设置下的检查点停顿，并不意味着每个推理请求都能获得相同改善。论文还测量了首 token 延迟和 token 间延迟，并报告了高并发 Llama-1B Chatbot 场景中较不利的表现。服务影响取决于工作负载，以及内存跟踪与框架同步点之间的相互作用。[^1]

## 查看代码与 artifact 评测记录

[FLASH 仓库](https://github.com/sept-usc/FLASH)提供修改后的 NVIDIA UVM 驱动、检查点与恢复程序，以及对照评测代码。复现需要文档指定的 H100 与 TDX 环境，并使用锁定版本的驱动、CUDA 和 vLLM。部署论文完整的远程证明与密钥释放服务，还需要在公开评测程序之外进一步集成。[^2]

[ATC artifact 评测结果](https://sysartifacts.github.io/atc2026/results)列出 FLASH 获得 Artifacts Available、Artifacts Evaluated – Functional 和 Results Reproduced 三项 badge。接受评测的 artifact 保存在 [Zenodo](https://doi.org/10.5281/zenodo.23199897)。这些 badge 表示会议记录的评测结果。[^3, 4]

:::analysis
FLASH 将机密 AI 服务需要同时考虑的两个要求联系起来：受保护状态必须能够恢复，恢复又必须保留完整性和新鲜性检查，使保存的状态具有明确含义。其实现展示了复用已有密文与在驱动中跟踪写入如何缩短检查点停顿。对于实际部署，还需要核对具体软件版本、恢复流程的集成方式，以及将密钥释放绑定到所接受检查点的可信服务。
:::
